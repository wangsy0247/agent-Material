# 可观测性工具使用指南

## 架构总览

```
应用代码 (Python)
  ├── Span ──OTLP (4318)──▶ Jaeger     ──▶ http://localhost:16686 (查链路)
  ├── /metrics (8000) ◀──抓── Prometheus ──▶ http://localhost:9090 (查指标)
  │                              │
  │                              └──▶ Grafana ──▶ http://localhost:3000 (看仪表板)
  └── JSON 日志 ──────────▶ logs/*.jsonl
```

| 工具 | 访问地址 | 角色 | 数据来源 |
|------|---------|------|---------|
| **Prometheus** | `http://localhost:9090` | 指标存储 + 查询 | 每 15 秒从应用 `/metrics` 端点抓取 |
| **Jaeger** | `http://localhost:16686` | 追踪链路查询 + 展示 | 应用通过 OTLP 推送 Span 数据 |
| **Grafana** | `http://localhost:3000` | 统一可视化仪表板 | 从 Prometheus 查询指标，从 Jaeger 跳转链路 |

## 二、Prometheus 使用指南

### 2.1 检查 Targets（确认抓取正常）

1. 打开 `http://localhost:9090`
2. 顶部 **Status → Targets**

你会看到：

```
agent_gateway        host.docker.internal:8000    State: UP    Last Scrape: 2s ago
rag_mcp_server       host.docker.internal:9090    State: DOWN  Last Scrape: 10s ago
```

- **UP** = Prometheus 成功从应用抓到了指标
- **DOWN** = `rag_mcp_server` 在 stdio 模式下没有 `/metrics` 端点，这是预期行为，不影响使用

### 2.2 基本查询（PromQL）

在顶部输入框输入查询语句，点 **Execute**。

#### 查当前值

```
http_request_total
```

返回所有 HTTP 请求的累计计数，按 `method`、`endpoint`、`status_code` 分组。

#### 查过去 5 分钟的每秒速率

```
rate(http_request_total[5m])
```

#### 查 P95 延迟

```
histogram_quantile(0.95, rate(http_request_duration_seconds_bucket[5m]))
```

#### 查当前活跃连接数

```
http_request_in_flight
```

#### 查 Agent 调用成功率

```
sum(rate(agent_invocation_total{status="success"}[5m]))
/
sum(rate(agent_invocation_total[5m]))
```

#### 查各 LangGraph 节点的耗时

```
rate(agent_graph_node_duration_seconds_sum[5m])
/
rate(agent_graph_node_duration_seconds_count[5m])
```

#### 查 RAG 检索各阶段延迟

```
rate(rag_retrieval_duration_seconds_sum[5m])
/
rate(rag_retrieval_duration_seconds_count[5m])
```

## 三、Jaeger 使用指南

### 3.1 搜索 Trace

1. 打开 `http://localhost:16686`
2. 填写搜索条件：

| 字段 | 含义 | 建议值 |
|------|------|--------|
| **Service** | 要查的服务 | `agent_material`（主服务）或 `rag_mcp_server`（RAG 检索） |
| **Operation** | 具体的操作名 | 通常留空（Any） |
| **Tags** | 按标签过滤 | 通常留空 |
| **Lookback** | 搜多久以内的数据 | 选包含你发测试请求的时间范围 |
| **Min Duration** | 只查慢于多少的请求 | 填 `1s` 过滤掉正常请求 |
| **Limit** | 最多返回多少条 | 默认 20 |

3. 点 **Find Traces**

### 3.2 看 Trace 列表

```
Found 15 traces

HTTP POST /api/v1/agent/chat    3.2s    2 spans    3分钟前
HTTP POST /api/v1/agent/chat    14.5s   3 spans    10分钟前   ← 这个慢
```

- 每行 = 一次完整的请求
- 彩色条形越长 = 这次请求越慢

### 3.3 看 Trace 详情（核心视图）

点击某一行，展开：

```
Trace ID: a1b2c3d4e5f67890    总耗时: 3.2秒    共 2 个服务

Service & Operation                    耗时      时间线
─────────────────────────────────────────────────────────────
agent_material: agent.react            3.2s   ████████████████
  rag_mcp_server: rag.search           2.8s      ██████████████
    vector.search                      0.03s     █
    rerank                             0.15s      ██
    llm.generate                       2.5s        ██████████
```

**怎么看**：

- **横向看时间线**：哪个 Span 的条形最长，哪个就是瓶颈。上图中 `llm.generate` 占了 2.5 秒，是主要瓶颈
- **纵向看层级**：缩进表示父子关系。外层 Span 的时间 = 所有内层 Span 之和
- **跨服务边界**：虚线或换行 = 请求从 Agent 进程跳到了 RAG MCP Server 进程

### 3.4 看 Span 详情

点击某个 Span（比如 `rerank`），右侧弹出详情面板：

```
Span: rerank
Service: rag_mcp_server
Duration: 150ms
Start Time: 100ms after trace start

Tags:
  input_docs        10
  output_docs       5
  top_score         0.9521
  model             qwen3-rerank
```

Tags 里的字段来自代码中的 `span.set_attribute("xxx", yyy)`。

### 3.5 对比两条 Trace

1. 搜索结果中勾选两条
2. 点 **Compare** 按钮

适合对比 "请求 A 为什么比请求 B 快"。

## 四、Grafana 使用指南

### 4.1 登录

打开 `http://localhost:3000`，配置了匿名访问会自动进入。

如果显示 Sign in，手动登录：

```
用户名: admin
密码:   admin
```

### 4.2 添加 Prometheus 数据源（首次配置，只需一次）

1. 左上角 ☰ → **Connections** → **Data sources**
2. 点 **Add data source** → 选 **Prometheus**
3. 填写：

```
URL: http://prometheus:9090
```

4. 点底部 **Save & test**，看到绿色 ✅ 即成功

> 如果找不到 Connections 菜单，直接访问 `http://localhost:3000/datasources`。

### 4.3 导入仪表板

1. 左上角 ☰ → **Dashboards**
2. 点右上角 **New** → **Import**
3. 把 `grafana_dashboard.json` 内容粘贴进去
4. 点 **Load → Import**

### 4.4 各面板解读

#### 第一行：HTTP 网关

| 面板 | 显示什么 | 健康状态 |
|------|---------|---------|
| HTTP QPS | 每秒请求数的曲线 | 平稳 = 正常，突然掉 0 = 服务挂了 |
| HTTP P50/P95/P99 | 三条线，请求延迟分布 | P99 与 P50 差距小 = 稳定；P99 突然飙到 P50 的 10 倍 = 有慢请求 |
| HTTP 错误率 | 大数字 | 0% = 正常；>1% = 排查 |
| 当前并发 | 大数字 | 高于平时 10 倍 = 可能被打爆 |

#### 第二行：Agent 推理

| 面板 | 显示什么 | 健康状态 |
|------|---------|---------|
| Agent 调用速率 | stream 和 invoke 各自的 QPS | 了解两种模式的使用占比 |
| 推理轮次分布 | 热力图 | 集中在 2-5 轮 = 正常；频繁出现 10 轮 = Agent 在死循环 |
| 推理延迟 P50/P95 | 两条线 | P95 > 30 秒 = 用户体感极差 |
| HITL/错误率 | 大数字 | 较高 = 敏感工具被频繁拦截或执行异常 |

#### 第三行：LangGraph 节点 + 流式输出

| 面板 | 显示什么 | 健康状态 |
|------|---------|---------|
| 节点耗时柱状图 | memory / agent / tools / summarize 等节点的平均耗时 | tools 最长 = MCP 工具慢；summarize 出现 = 对话过长触发了压缩 |
| 首 Token 延迟 | P50 和 P95 | < 0.5 秒 = 流畅；> 2 秒 = 用户感觉卡 |

#### 第四行：LLM 调用 + MCP

| 面板 | 显示什么 | 健康状态 |
|------|---------|---------|
| LLM 调用速率 | 按用途（推理/生成/分类）分色 | 了解 LLM 调用分布 |
| LLM P95 延迟 | 按用途分 | 不同目的下 LLM 的性能差异 |
| Token 消耗速率 | input 和 output | output 线持续高 = 回答偏长，成本高 |
| MCP Tool Call 速率 | 按工具名分 | 哪个 RAG 工具被调用最多 |

#### 第五行：RAG 检索 + DashScope

| 面板 | 显示什么 | 健康状态 |
|------|---------|---------|
| 检索各阶段延迟 | 柱状图（向量/BM25/融合/重排序/父chunk查询） | rerank 柱异常高 = DashScope 重排序 API 出问题 |
| 空结果率 | 曲线 | 持续高 = 知识库内容不足或 query 改写失败 |
| DashScope API 延迟 | rerank 和 embedding 各自的 P95 | 哪个 API 慢一目了然 |
| DashScope 限流/重试 | 两条曲线 | 出现就说明 API 配额不够或用得太猛 |

#### 第六行：任务队列

| 面板 | 显示什么 | 健康状态 |
|------|---------|---------|
| 任务队列深度 | pending/processing/failed/completed 四个柱 | pending 不断增长 = Worker 处理不过来 |
| 任务处理耗时 | 按类型（ingest/delete/reindex）分 | 突然变长 = 文档变大了或数据库慢了 |
| Worker 空闲时间 | 大数字 | 一直为 0 = Worker 持续忙碌 |

### 4.5 时间选择器

页面顶部的时间选择器支持：

- 快速选择：Last 5 minutes / Last 1 hour / Last 24 hours
- 拖选：在图表上直接拖拽一个范围
- 刷新：右上角可以设置自动刷新间隔

## 五、三者协作排查套路

```
例行检查：打开 Grafana http://localhost:3000
  │
  ├── 全部绿色 → 正常，关闭
  │
  └── 某个面板异常
        │
        ├── HTTP 错误率上升
        │     └── Jaeger 搜 error=true 的 Trace → 看 span 的 error.message → 定位异常原因
        │
        ├── P99 延迟飙升
        │     └── Grafana 向下翻，找到同样飙高的子面板
        │           ├── LLM 面板飙 → LLM 模型慢 → 检查 API 限流或切换模型
        │           ├── RAG rerank 面板飙 → DashScope 限流面板确认 → 提工单加配额
        │           ├── LangGraph tools 节点飙 → 去 Jaeger 查具体哪个 MCP 工具慢
        │           └── LangGraph summarize 节点飙 → 对话太长触发压缩 → 增加上下文窗口
        │
        ├── Agent 推理轮次频繁到 10 轮
        │     └── Agent 在死循环 → Jaeger 搜那段时间的 Trace → 看 tool_calls 序列：
        │           同一工具被连续调用 3+ 次 = Agent 陷入执行→失败→重试的循环
        │
        └── 空结果率上升
              └── 知识库覆盖不足 → 补充文档, 或者 query 改写策略需要调整

定位具体请求：
  Grafana 记下异常时间 → Jaeger 用同时间范围搜索 → 找到慢 Trace → 展开看 Span 详情
```

## 六、常用 PromQL 速查

| 目的 | PromQL 查询语句 |
|------|---------------|
| HTTP 每秒请求数 | `rate(http_request_total[5m])` |
| HTTP P95 延迟 | `histogram_quantile(0.95, rate(http_request_duration_seconds_bucket[5m]))` |
| 当前活跃连接 | `http_request_in_flight` |
| Agent 成功率 | `sum(rate(agent_invocation_total{status="success"}[5m])) / sum(rate(agent_invocation_total[5m]))` |
| 各 LangGraph 节点耗时 | `rate(agent_graph_node_duration_seconds_sum[5m]) / rate(agent_graph_node_duration_seconds_count[5m])` |
| RAG 检索各阶段耗时 | `rate(rag_retrieval_duration_seconds_sum[5m]) / rate(rag_retrieval_duration_seconds_count[5m])` |
| MCP 工具调用速率 | `sum(rate(mcp_tool_call_total[5m])) by (tool)` |
| LLM Token 消耗速率 | `rate(agent_llm_token_total[5m])` |
| DashScope API 调用速率 | `sum(rate(dashscope_api_total[5m])) by (api)` |

## 七、常见问题

### Q: Grafana 显示 No data

可能原因：

1. **应用没启动** — 确认 `uvicorn` 在运行
2. **Prometheus 数据源没配** — 检查 Data Sources 里 Prometheus URL 是否正确
3. **时间范围不对** — 选的时间范围在应用启动之前
4. **指标名写错了** — Prometheus 里先查一下指标名是否存在

### Q: Jaeger 搜不到 Trace

1. **应用没发数据** — 检查 `opentelemetry-exporter-otlp-proto-http` 是否安装
2. **Jaeger 端口不通** — `curl http://localhost:4318` 确认 Jaeger 在线
3. **时间范围不对** — Lookback 改大一点

### Q: host.docker.internal 不通

WSL2 原生 Docker（非 Docker Desktop）中这个域名可能不存在。替代方案：

```bash
# 获取 WSL2 的 IP
hostname -I | awk '{print $1}'
# 把 prometheus.yml 中的 host.docker.internal 换成这个 IP
```

### Q: 指标太多，存储满了

```bash
# 清理 Prometheus 数据
docker-compose -f docker-compose.observability.yaml down -v
docker-compose -f docker-compose.observability.yaml up -d
```
