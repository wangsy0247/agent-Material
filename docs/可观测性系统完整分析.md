### 三层可观测性

| 层 | 名称 | 数据格式 | 输出目的地 | 用途 |
|-----|------|----------|-----------|------|
| **L1** | 结构化日志 | JSON，每行一条 (`jsonl`) | 文件 → Promtail → Loki → Grafana | 人类可读的事件记录，带 `trace_id` 可关联追踪 |
| **L2** | 分布式追踪 | OpenTelemetry Span (W3C Trace Context) | OTLP HTTP → Jaeger | 跨进程调用链路分析，性能瓶颈定位 |
| **L2b** | LLM 追踪 | LangFuse Trace | HTTP → LangFuse → ClickHouse | LLM 调用专属：Token 消耗、成本、质量评分 |
| **L3** | 时序指标 | Prometheus 文本格式 | HTTP `/metrics` → Prometheus → Grafana | 聚合统计：QPS、延迟分位数、错误率、资源状态 |

## 三、L1 — 结构化日志系统

### 3.1 设计原理

采用 **JSON 行格式**（每行一条完整 JSON），与 Loki/Promtail 原生集成。日志通过 `contextvars` 自动携带追踪上下文（`trace_id`、`span_id`）和请求上下文（`request_id`、`session_id`、`user_id`），实现日志与分布式追踪的自动关联。

### 3.2 核心组件

#### `structured_logger.py` — JsonFormatter + 上下文字典

**文件位置**：
- Agent 侧: `backend/packages/agent_material/observability/structured_logger.py`
- RAG 侧: `rag_mcp_server/observability/structured_logger.py`（结构相同）

**工作原理**：

```python
# contextvars — 跨 asyncio 任务自动传播
_trace_context: contextvars.ContextVar[dict]   # trace_id + span_id
_request_context: contextvars.ContextVar[dict] # request_id + session_id + user_id
```

每条日志输出为：

```json
{
  "timestamp": "2026-06-11T08:30:00.123456+00:00",
  "level": "INFO",
  "service": "agent_material",
  "component": "React_agent",
  "file": "React_agent.py:156",
  "message": "Agent 推理完成",
  "trace_id": "a1b2c3d4e5f67890",
  "span_id": "1234abcd",
  "request_id": "req_abc123def456",
  "session_id": "sess_xyz",
  "user_id": "default",
  "exception": "..."   // 仅在有异常时出现
}
```

**关键函数**：

| 函数 | 用途 | 调用时机 |
|------|------|---------|
| `get_logger(name)` | 获取 JSON 格式 Logger（自动创建 FileHandler + StreamHandler） | 模块初始化时 |
| `set_trace_context(trace_id, span_id)` | 设置当前协程的追踪上下文 | OTel Span 创建时 |
| `set_request_context(request_id, session_id, user_id)` | 设置当前协程的请求上下文 | HTTP 请求入口 |
| `get_trace_context()` | 读取当前追踪上下文 | 需要手动注入 trace_id 时 |
| `get_request_context()` | 读取当前请求上下文 | 需要手动注入 request_id 时 |

**日志输出目录**：`logs/` 下，文件名为 `{组件名}.jsonl`（如 `gateway_app.jsonl`、`React_agent.jsonl`、`rag_service.jsonl`）。

### 3.3 日志 → Loki 数据流

```
Python 应用写入 logs/*.jsonl
       │
       ▼
Promtail (docker 容器)
  - 监控 /logs/gateway*.jsonl (job: agent_gateway_logs)
  - 监控 /logs/server*.jsonl  (job: rag_mcp_server_logs)
  - pipeline_stages:
      1. json 解析 → 提取 timestamp / level / message / trace_id / span_id / request_id 等
      2. timestamp → 识别 ISO 8601 时间戳（RFC3339）
      3. labels → 将 level / component / trace_id / request_id 提升为 Loki 标签
       │
       ▼
Loki (日志聚合器，类 Prometheus 查询语言 LogQL)
       │
       ▼
Grafana → Explore 面板中按 trace_id 搜索关联日志
```

## 四、L2 — OpenTelemetry 分布式追踪

### 4.1 设计原理

采用 **W3C Trace Context** 标准实现跨进程追踪传播。使用 `OTLPSpanExporter`（HTTP 协议）将 Span 批量导出到 Jaeger，完整复现一个用户请求从 HTTP 入口 → Agent 推理 → MCP 工具调用 → RAG 检索的全链路。

### 4.2 核心组件

#### `otel_setup.py` — SDK 初始化

```python
# 默认配置
OTEL_EXPORTER_OTLP_ENDPOINT = "http://localhost:4318/v1/traces"  # Jaeger OTLP HTTP 接收端
OTEL_SERVICE_NAME           = "agent_material" / "rag_mcp_server"

# BatchSpanProcessor 参数
max_queue_size        = 2048   # 缓冲区最大 Span 数（超出丢弃）
max_export_batch_size = 512    # 每次批量导出上限
schedule_delay_millis = 5000   # 批量导出发送间隔（ms）
```

**优雅降级策略**：
- 如果 `opentelemetry-exporter-otlp` 未安装 → 降级为 `ConsoleSpanExporter`（打印到 stdout）
- `init_otel()` 被 `try/except` 包裹 → 初始化失败不影响业务

```python
# backend/app/gateway/app.py — lifespan 中调用
from agent_material.observability import init_all
init_all(service_name="agent_material")  # 幂等，重复调用不重复初始化
```

#### `mcp_trace.py` — 跨进程 TraceContext 传播

这是整个可观测性系统中最关键的设计。Agent Gateway 和 RAG MCP Server 是两个独立进程，通过 MCP JSON-RPC 协议通信。为了让 Jaeger 里显示完整的端到端调用链，需要在 JSON-RPC 层面传递 W3C Trace Context。

**发送端（Agent → MCP 工具调用）**：

```python
# backend/packages/agent_material/mcp/tools.py
def inject_trace_context(tool_args):
    from opentelemetry.propagate import inject
    carrier = {}
    inject(carrier)  # 从当前 OTel Context 提取 traceparent + tracestate
    tool_args.setdefault("_meta", {})
    tool_args["_meta"]["traceparent"] = carrier["traceparent"]
    tool_args["_meta"]["tracestate"] = carrier.get("tracestate", "")
```

**接收端（RAG MCP Server → 恢复 Span 上下文）**：

```python
# rag_mcp_server/server.py — MCP 工具处理函数
def extract_trace_context(tracing_meta):
    from opentelemetry.propagate import extract
    ctx = extract({"traceparent": tracing_meta["traceparent"],
                   "tracestate": tracing_meta.get("tracestate", "")})
    # 在此 ctx 下创建子 Span
    with tracer.start_as_current_span("rag.search", context=ctx):
        ...
```

**效果**：在 Jaeger UI 中可以看到如下调用链：
```
HTTP POST /api/v1/agent/chat  (FastAPIInstrumentor 自动创建)
  └── agent.reasoning          (LangGraph agent_node)
        └── mcp_tool_call.rag_query  (MCP 工具调用包装器)
              └── rag.search          (跨进程: RAG MCP Server)
                    ├── vector_search     (PGVector 检索)
                    ├── bm25_search       (BM25 关键词)
                    ├── rrf_fusion        (RRF 融合)
                    ├── rerank            (CrossEncoder 重排序)
                    └── llm.call          (RAG 总结生成)
```

#### OpenTelemetry Callback（RAG 侧 LangChain 集成）

```python
# rag_mcp_server/observability/otel_callback.py
class OpenTelemetryCallback(BaseCallbackHandler):
    # 将 LangChain 组件生命周期映射为 OTel Span：
    on_llm_start/end        → span "llm.call" (模型名、提示统计、Token 用量)
```

### 4.3 FastAPI HTTP 自动追踪

```python
# backend/app/gateway/app.py
from opentelemetry.instrumentation.fastapi import FastAPIInstrumentor
FastAPIInstrumentor.instrument_app(
    app,
    excluded_urls="/metrics,/health,/docs,/redoc,/openapi.json",
)
```

FastAPIInstrumentor 会自动为每个 HTTP 请求创建一个顶层 Span，名称格式为 `HTTP {METHOD} {route}`，包含属性：
- `http.method`、`http.url`、`http.status_code`
- `http.request_content_length`、`http.response_content_length`
- `net.peer.ip`、`http.user_agent`

排除规则：`/metrics`、`/health`、`/docs` 等运维端点不创建 Span，避免噪音。

## 五、L2b — LangFuse LLM 追踪

### 5.1 设计原理

LangFuse 是一个开源 LLM 可观测性平台（MIT 协议），专注于 LLM 调用的全生命周期追踪：
- **Token 消耗统计**：按模型/目的分组，计算成本
- **延迟分解**：流式首 Token 延迟、总耗时
- **质量评估**：支持人工评分反馈闭环
- **Session 分组**：按用户会话聚合多轮对话

本项目从 LangSmith 切换到 LangFuse 的核心原因：LangFuse 支持 Docker 自部署，无需翻墙、无数据出境风险。

## 六、L3 — Prometheus 时序指标

### 6.1 设计原理

采用 **RED 方法论**（Rate / Error / Duration）为 HTTP、Agent、LLM、检索、队列等维度设计指标。分为两个独立的 `CollectorRegistry`，分别暴露在 Agent Gateway（`/metrics`）和 RAG MCP Server（`:9090/metrics`）上，Prometheus 每 15s 抓取一次。

### 6.2 Agent Gateway 指标（58 个）

#### 6.2.1 HTTP / Gateway 指标

| 指标名称 | 类型 | 标签 | 说明 |
|----------|------|------|------|
| `gateway_http_request_total` | Counter | `method`, `endpoint`, `status_code` | HTTP 请求计数 |
| `gateway_http_request_duration_seconds` | Histogram | `method`, `endpoint` | 请求延迟分布（buckets: 10ms ~ 60s） |
| `gateway_http_request_in_flight` | Gauge | `method` | 当前处理中的请求数 |

#### 6.2.2 Agent 推理指标

| 指标名称 | 类型 | 标签 | 说明 |
|----------|------|------|------|
| `agent_invocation_total` | Counter | `mode` (stream/invoke/resume), `status` (success/hittl_interrupt/error/max_iterations) | Agent 调用总数 |
| `agent_iteration_count` | Histogram | — | 推理轮次分布（buckets: 1~15） |
| `agent_duration_seconds` | Histogram | `mode` | Agent 总执行时间（buckets: 0.5s ~ 300s） |

#### 6.2.3 LangGraph 节点指标

| 指标名称 | 类型 | 标签 | 说明 |
|----------|------|------|------|
| `agent_graph_node_duration_seconds` | Histogram | `node` (memory/summarization/agent/human_approval/tools/finalize) | 各节点执行延迟 |
| `agent_graph_node_iterations_total` | Counter | `node` | 各节点执行次数 |

#### 6.2.4 LLM 调用指标

| 指标名称 | 类型 | 标签 | 说明 |

| `agent_llm_call_duration_seconds` | Histogram | `model`, `purpose` | LLM 调用延迟 |

### 6.4 StreamMetrics 工具类

两个服务各自实现了 `StreamMetrics` 类，通过包装流式生成器自动收集首 Token 延迟、Chunk 计数、Chunk 间隔等指标：

```python
# Agent 侧 (异步流式)
stream_metrics = StreamMetrics(mode="agent_chat")
async for chunk in stream_metrics.awrap(agent_graph.astream(...)):
    yield f"data: {json.dumps(chunk)}\n\n"
# 流结束后自动上报: first_token_latency, total_chunks, duration

# RAG 侧 (同步流式)
sm = StreamMetrics(model="qwen3.6-plus", purpose="rag_generate")
for chunk in sm.wrap(llm.stream(...)):
    yield chunk
# 流结束后自动上报: first_token_latency, chunk_count, tokens_per_second, inter_chunk_latency
```

## 十二、故障排查

### 12.1 Jaeger UI 中没有 Span

1. 确认 Jaeger 容器运行：`docker ps | grep jaeger`
2. 确认 OTLP 端点可达：`curl -X POST http://localhost:4318/v1/traces`
3. 确认环境变量：`OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4318/v1/traces`
4. 确认 `opentelemetry-exporter-otlp` 已安装

### 12.2 Prometheus 目标显示 DOWN

1. 确认 Agent Gateway 在 `0.0.0.0:8080` 启动（非 `127.0.0.1:8080`）
   - Docker 通过 `host.docker.internal` 访问宿主机，`127.0.0.1` 指向容器自身
2. 检查 `/metrics` 端点：`curl http://localhost:8080/metrics`
3. 检查 Prometheus targets：http://localhost:9090/targets

### 12.3 Grafana 仪表板无数据

1. 确认数据源配置正确
   - Prometheus: `http://prometheus:9090`
   - Loki: `http://loki:3100`
   - Jaeger: `http://jaeger:16686`
2. Grafana 容器必须与 Prometheus/Loki/Jaeger 在同一 Docker 网络

### 12.4 LangFuse 追踪未出现

1. 确认 `LANGFUSE_SECRET_KEY` 已设置
2. 确认 LangFuse 容器运行：`docker logs langfuse`
3. 检查应用日志中的 LangFuse 初始化信息
4. 确认 `langfuse` Python SDK 已安装：`pip install langfuse`

### 12.5 LangFuse 容器启动失败

| 错误 | 原因 | 解决 |
|------|------|------|
| `CLICKHOUSE_URL is not configured` | v3 需要 ClickHouse | 已在 docker-compose 中添加 |
| `failed to parse scheme from database URL: no scheme` | 缺少 `CLICKHOUSE_MIGRATION_URL` | 添加 `clickhouse://user:pass@host:9000` |
| `Langfuse requires a bucket name for S3` | v3 需要 S3 存储 | 已添加 MinIO + 环境变量 |
| `Cannot set property message` | Node.js 20 + Next.js 14.2.21 不兼容 | 已通过 `error-polyfill.js` 修复（需要 `--require` 加载） |

### 12.6 日志未出现在 Grafana

1. 确认 `logs/` 目录下有 `.jsonl` 文件
2. 确认 Promtail 能读取日志目录：`docker logs promtail`
3. 确认 Loki 可达：`curl http://localhost:3100/ready`
4. 检查 Promtail 配置中 `__path__` 匹配正确的文件模式

### 12.7 pgvector 容器启动失败

```
initdb: error: directory "/var/lib/postgresql/data" exists but is not empty
```
使用已有数据卷时，确保 `PGDATA` 指向正确的路径。如果数据在命名卷 `pg16_data` 中，直接用 `-v pg16_data:/var/lib/postgresql/data` 挂载即可。

### 13.1 设计原则

1. **静默降级**：所有埋点代码必须被 `try/except` 包裹，可观测性基础设施不可用时不影响业务
2. **延迟导入**：Prometheus 指标、OTel SDK 等重量级模块使用懒加载，避免 import 副作用
3. **幂等初始化**：`ensure_initialized()` 保证多次调用不重复创建 TracerProvider
4. **ContextVar 传播**：日志和追踪上下文通过 `contextvars` 跨 asyncio 任务自动传播，无需显式传参
5. **标签区分**：所有指标使用标签区分维度（如 `model`、`purpose`、`status`），避免高基数标签

#### 13.3.4 🔑 `track_stage` 上下文管理器 — 阶段延迟追踪

这是项目中最常用的指标埋点模式之一，用上下文管理器自动记录一个阶段的延迟和文档数。

**Agent 侧**（`backend/packages/agent_material/observability/metrics.py:213-224`）：

```python
from agent_material.observability.metrics import track_stage

with track_stage("my_stage", doc_count=len(results)):
    results = do_something()
# 退出时自动 recording: stage_duration + doc_count
```

**RAG 侧**（`rag_mcp_server/observability/metrics.py:335-350`）：

```python
from rag_mcp_server.observability.metrics import track_stage

with track_stage("vector_search", doc_count=len(docs)):
    docs = vector_store.similarity_search(query)
# 自动记录: rag_retrieval_duration_seconds{stage="vector_search"} + rag_retrieval_docs_count{stage="vector_search"}
```

**实现原理**：

```python
@contextmanager
def track_stage(stage: str, doc_count: int = 0):
    start = time.time()
    try:
        yield
    finally:
        elapsed = time.time() - start
        retrieval_duration.labels(stage=stage).observe(elapsed)
        if doc_count > 0:
            retrieval_docs.labels(stage=stage).observe(doc_count)
```

#### 13.3.6 🔑 `_timed_node` — Graph 节点计时装饰器

Agent 中每个 LangGraph 节点都用此装饰器自动计时（`agent_graph.py:645-671`）：

```python
def _timed_node(name: str, fn):
    """装饰器：为 LangGraph 节点函数添加延迟指标追踪。"""
    async def wrapper(state, *args, **kwargs):
        t0 = time.time()
        result = await fn(state, *args, **kwargs)
        elapsed = time.time() - t0
        graph_node_duration.labels(node=name).observe(elapsed)
        graph_node_iterations.labels(node=name).inc()
        logger.debug("node_timing", extra={"node": name, "duration_ms": elapsed * 1000})
        return result
    return wrapper

# 使用
graph.add_node("memory", _timed_node("memory", partial(memory_node, ...)))
graph.add_node("agent", _timed_node("agent", partial(agent_node, ...)))
graph.add_node("tools", _timed_node("tools", tool_node))
```

#### 13.3.7 🔑 `_LLMTracker` — LLM 调用追踪器

RAG 侧用上下文管理器追踪 LLM 调用，自动分类错误类型（`rag_mcp_server/observability/metrics.py:357-396`）：

```python
from rag_mcp_server.observability.metrics import track_llm_call

# 基本用法
with track_llm_call(model="qwen3.6-plus", purpose="rag_generate") as tracker:
    response = llm.invoke(messages)
    tracker.record_tokens(input_tokens=1200, output_tokens=800)
# 自动记录:
#   rag_llm_call_total{model="qwen3.6-plus", purpose="rag_generate"}
#   rag_llm_call_duration_seconds{...}
#   rag_llm_token_total{type="input"} / {type="output"} / {type="total"}
# 如果异常自动分类: timeout / rate_limit / api_error / unknown
```

**实现原理**：

```python
class _LLMTracker:
    def __exit__(self, exc_type, exc_val, exc_tb):
        elapsed = time.time() - self._start
        if exc_type:
            llm_call_total.labels(...).inc()
            error_type = _classify_error(exc_val)
            llm_call_error_total.labels(model=..., error_type=error_type).inc()
        else:
            llm_call_total.labels(...).inc()
            llm_call_duration.labels(...).observe(elapsed)
        return False  # 不吞异常

def _classify_error(exc) -> str:
    msg = str(exc).lower()
    if "timeout" in msg:  return "timeout"
    if "rate" in msg or "429" in msg or "limit" in msg:  return "rate_limit"
    if "4" in msg[:3] or "5" in msg[:3]:  return "api_error"
    return "unknown"
```

### 13.7 埋点巡检清单

新增功能时，用以下清单确保覆盖了所有可观测性维度：

| 序号 | 检查项 | 防遗漏提示 |
|------|--------|-----------|
| 1 | **关键操作**有对应日志 (INFO/DEBUG) | 用 `logger.info("操作名", extra={...})` |
| 2 | **异常路径**有对应日志 (ERROR + exc_info) | 用 `logger.error("...", exc_info=True)` |
| 3 | **请求入口**设置了 `set_request_context` | 保证后续所有日志带 request_id |
| 4 | **HTTP 端点**有 RED 指标 (rate/error/duration) | Counter + Histogram + Gauge |
| 5 | **LLM 调用**有 Token 指标 (input/output/total) | 使用 `track_llm_call` 或手动 `Counter.inc()` |
| 6 | **检索调用**有阶段延迟指标 | 使用 `track_stage` 上下文管理器 |
| 7 | **流式输出**有 StreamMetrics 包装 | 用 `sm.awrap(stream)` 或 `sm.wrap(stream)` |
| 8 | **MCP 工具调用**前调用了 `inject_trace_context` | 保证跨进程追踪链路不断 |
| 9 | **MCP 工具端**调用了 `extract_trace_context` | 在父 context 下创建子 Span |
| 10 | **LangChain 调用**传入了 `get_run_config()` | 保证 LangFuse 追踪数据完整 |
| 11 | **新增指标**注册到了正确的 Registry | Agent 侧用 `agent_material.observability.metrics.REGISTRY`，RAG 侧用 `rag_mcp_server.observability.metrics.REGISTRY` |
| 12 | **Histogram 的 buckets**覆盖了预期值范围 | 太小截断数据，太大降低精度 |
| 13 | **Counter 以 `_total` 结尾** | Prometheus 命名约定 |
| 14 | **指标名称**以小写字母开头，用下划线分隔 | `my_operation_duration_seconds` |
| 15 | **所有埋点代码**在 try/except 中 | 可观测性失败不影响业务 |

## 十四、架构决策记录

| 决策 | 原因 |
|------|------|
| **LangSmith → LangFuse** | LangFuse 开源、MIT 协议、Docker 自部署，无需翻墙，无数据出境 |
| **Jaeger (非 Grafana Tempo)** | Jaeger all-in-one 镜像体积小（~80MB），部署最简单 |
| **LangFuse v3 (非 v2)** | v3 用 ClickHouse 列式存储分析数据，查询性能大幅提升 |
| **MinIO (非直接写 ClickHouse)** | LangFuse v3 架构要求 S3 作为事件上传中间层 |
| **W3C Trace Context (非 B3)** | W3C 是业界标准，与其他系统互操作性最好 |
| **双 Registry** | Agent Gateway 和 RAG MCP Server 是两个独立进程，各自暴露 `/metrics` |
| **JSON 行日志 (非 syslog)** | 与 Loki/Promtail 原生集成，无需额外解析层 |
| **pgvector 在容器内 (非外部 DB)** | 降低部署复杂度，但生产环境应考虑独立数据库 |
