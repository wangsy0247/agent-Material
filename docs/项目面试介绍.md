# Agent Material 项目面试介绍

> 本文档用于面试时介绍本项目，建议按“项目概述 → 技术栈 → 核心亮点 → 亮点详解”的结构进行讲解。

---

## 一、项目概述：这是什么，解决了什么问题

### 项目定位

**Agent Material** 是一个基于大语言模型 + RAG（检索增强生成）的垂直领域智能问答系统，专注于**材料科学文献与私有知识的智能检索、理解、推理与问答**。

### 解决的核心问题

1. **大模型在专业领域“幻觉”严重**：通用 LLM 对材料科学专业概念、公式、实验数据容易编造。
2. **无法访问私有/最新知识库**：大量材料科学文献（PDF）没有被大模型预训练覆盖，需要把私有文档接入问答链路。
3. **长文档理解与检索效率低**：单篇论文几十页，传统关键词检索召回率低，需要语义检索 + 重排序。
4. **多轮对话缺乏记忆**：科研问答往往是长会话，需要短期、中期、长期三层记忆协同。
5. **检索链路黑盒不可观测**：需要追踪“查了什么、召回什么、为什么这样答”，便于调优与面试。

### 一句话总结

> 通过构建“文档解析 → 多粒度向量化 → 混合检索 → 重排序 → 大模型生成 → 记忆沉淀 → 可观测追踪”的完整 RAG 链路，让大模型能够基于私有材料科学文献进行可信、可溯源、可记忆的专业问答。

## 二、技术栈

| 层级 | 技术 |
|------|------|
| **后端框架** | Python、FastAPI |

## 四、核心亮点详解

### 亮点 1：多粒度索引架构（Multi-Granularity Indexing）

#### 问题背景

RAG 中 chunk 大小是个经典 trade-off：chunk 太小会丢失上下文，chunk 太大会稀释细节。针对材料科学论文，既需要“精准定位某一句话”，又需要“理解整段实验背景”。

#### 方案

实现双层 collection 索引：

- **`agent_small`**：小 chunk（如 500 tokens），用于精准语义定位。
- **`agent_large`**：大 chunk（如 2000 tokens，Parent-Child 结构），用于保留上下文。

#### 面试话术

> 我设计了一个 Parent-Child 多粒度索引：小 chunk 做向量检索保证召回精度，大 chunk 作为父文档补充上下文。检索时先命中小 chunk，再回查对应父文档，兼顾精度与上下文完整性。

---

### 亮点 2：混合检索 + 精排链路

#### 问题背景

纯向量检索对专业术语、人名、化学式、材料 ID（如 `LiFePO4`、`β-Ga2O3`）效果不稳定；纯 BM25 又缺乏语义理解能力。

#### 方案

- **向量检索**：PGVector + HNSW 索引，cosine distance 转 similarity，带阈值过滤。
- **关键词检索**：BM25Retriever，弥补专业术语召回。
- **RRF 融合**：`EnsembleRetriever` 融合两者结果。
- **精排**：调用 DashScope `qwen3-rerank` API 对 Top-K 结果重排序，降低 CrossEncoder 本地部署成本。

#### 面试话术

> 我的检索链路不是单一向量检索，而是“向量 + BM25 混合召回 + API 重排序”。针对材料领域的化学式、材料 ID 等关键词，BM25 能补上向量检索的短板；重排序阶段用 DashScope 的 rerank API，既保证精度又避免本地 GPU 依赖。

---

### 亮点 3：查询理解与查询改写

#### 问题背景

用户问题可能是闲聊、与领域无关、或表述模糊，直接走 RAG 会浪费检索资源；科研问题常需要拆解、扩展、多角度检索。

#### 方案

- **Query Routing**：先识别“闲聊 / 无关问题 / 事实性问题 / 总结性问题 / 对比性问题”，决定是否走 RAG。
- **Query Rewriting**：支持 Step-back、HyDE、查询扩展、子问题分解等策略，自动生成多个检索变体。
- **HyDE 模式**：让模型先生成假设文档，再用假设文档的 embedding 做检索，提升召回相关性。

#### 面试话术

> 我在检索前加了 Query Router 判断问题类型：闲聊直接回答，无关问题拦截，科研问题才进入 RAG。同时支持 Step-back、HyDE、查询扩展等改写策略，比如把“这种材料导热性怎么样”改写成更具体的学术检索表达式，提升召回质量。

---

### 亮点 4：三层记忆系统

#### 问题背景

科研问答是长会话，需要让 Agent“记得”用户偏好、项目背景、之前讨论过的材料与结论。

#### 方案

- **L1 短期记忆**：LangGraph State，维护当前对话消息与 token 预算，超出阈值触发 Summarization。
- **L2 中期记忆**：SQLite（`memory_sessions.db`），持久化会话元数据与完整消息历史，按 `user_id` 隔离。
- **L3 长期记忆**：PGVector + Markdown 文件，自动从对话中提取“用户画像 / 项目知识 / 事实 / 任务”，写入向量库与分类文件，后续对话自动召回。

#### 面试话术

> 我设计了三层记忆：短期记忆维护当前上下文，中期记忆用 SQLite 存会话历史，长期记忆则自动从对话里抽取关键事实写入 PGVector 和 Markdown 文件。这样用户隔几天再问“上次那个电池材料”时，系统能自动召回相关背景。

---

### 亮点 5：工程化可观测与评估闭环

#### 问题背景

RAG 系统上线后最难的是“知道为什么答错”——是文档没召回、重排序错了、还是模型生成偏差？

#### 方案

- **可观测性栈**：LangFuse 记录完整 LLM Trace；Jaeger 做分布式追踪；Prometheus + Grafana 监控指标；Loki + Promtail 聚合日志。
- **RAGAS 评估**：用 `ragas_eval_dataset.json` 等数据集评估 `faithfulness`、`answer_relevancy`、`context_precision`、`context_recall` 等指标。
- **后台任务队列**：SQLite 驱动的 `rag_queue.db`，实现文档增量索引的异步处理，避免阻塞 API。

#### 面试话术

> 我搭了一套完整的可观测链路：LangFuse 记录每次问答的检索与生成过程，Jaeger 追踪调用链，Prometheus/Grafana 监控延迟与召回指标，Loki 聚合日志。同时用 RAGAS 做离线评估，形成“指标监控 → 问题定位 → 策略迭代”的闭环。
